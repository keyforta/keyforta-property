# OPS-001 / OPS-002 pipeline container build optimization

## Scope

Reduce elapsed GitHub Actions time by running the independent API and web
container build work concurrently. Keep every existing verification,
authorization, plan, deployment, migration, smoke-test, and evidence gate.

## Requirements

Both image operations must finish successfully before the workflow advances.
Each image must retain its existing immutable tag, Dockerfile, build context,
registry destination, and downstream use.

## Risks

Naive background processes can hide a failed child when the other child exits
successfully. Each child PID therefore requires an explicit wait and captured
exit status before a combined fail-closed result.

## Design

Use one named build step in each workflow. Start API and web builds in parallel,
retain their process IDs, wait for both even if one fails, and reject the step if
either exit status is nonzero. Deployment defers both registry pushes until both
builds pass, preserving the prior all-builds-before-publication ordering.

## Baseline

GitHub Actions run `34730923412` spent 35 seconds building the API image and 48
seconds building the web image sequentially. Deployment run `34741021709` spent
2 minutes 4 seconds building and pushing the two images sequentially within one
step. End-to-end durations were about 4 minutes for CI and 14 minutes for deploy.

## Rollback

Revert the workflow commit to restore the two sequential CI build steps and the
sequential deployment build/push commands. No application, database, or Azure
resource rollback is required.

## Tests

The committed Node test parses both YAML files and executes their exact build
run blocks against deterministic `docker` and `az` fakes. It covers success, API
failure, web failure, dual failure, real process overlap, and the rule that deploy
publishes neither image after a build failure. Every failure case asserts that
both children completed, preventing an unguarded first wait from passing. CI
executes this test before the real image builds. Canonical verification then
exercises repository policy, task scope, tests, builds, and Bicep compilation.

## Results

Both workflows now start their API and web container builds concurrently, capture
each PID, wait for both children, emit a component-specific GitHub error for
either failure, and require both statuses to be zero before continuing. Deploy
pushes the two images only after that combined build gate passes.

Workflow YAML parsing, Prettier validation, and Bash syntax validation passed.
The initial six ad hoc child-process scenarios passed. Independent review then
identified that combining each deployment build and push could publish one image
when its peer build failed, and that the scenarios were not durable. The repair
separates publication from concurrent builds and adds a committed Node test
covering nine workflow scenarios, including dual failures and no partial push.

The attempted local Docker execution could not connect to the Docker Desktop
daemon, so it did not evaluate image contents or timing. Hosted CI remains the
required clean-runner validation for the real concurrent image builds.

## Coverage

- CI retains the web public-asset check after both images finish building.
- Deployment retains immutable SHA tags, builds both images successfully before
  either push, and pushes both before migration and application deployment.
- All plan, authorization, database migration, smoke-test, and evidence steps are
  unchanged.
- Canonical verification passed repository policy, contract, classification,
  lifecycle, governance, formatting, lint, typecheck, tests, architecture,
  secrets, documentation, harness self-test, production build, and six-file
  Bicep compilation.

## Failure

The first canonical run stopped at formatting because the new Markdown evidence
and JSON task contract were not Prettier-normalized. A later local container
check could not start either image build because Docker Desktop was not running;
both logs reported an unavailable Docker socket.

The first repair-cycle canonical run rejected custom required-command and
required-scenario labels that are outside the verifier's governed vocabulary.

## Bounded Correction

Prettier normalized only the two new governance artifacts, after which the same
canonical command passed. No code correction was appropriate for the unavailable
local Docker daemon; hosted CI will execute both real builds on its Docker-enabled
runner.

Independent security review found a partial-publication risk in the first deploy
implementation, and independent PR review found that its behavior checks were not
committed. Repair cycle 2 restores all-builds-before-publication ordering and adds
deterministic offline regression coverage under `.github/tests`.

Repair cycle 3 wires that test into CI and retains the contract's supported
`canonical-verification` scenario and `pnpm verify:all` command.

Independent follow-up review found that the failure assertions did not prove both
children completed. The test now records and requires both completion events in
all failure combinations, with a process-level timeout for deadlock detection.
The focused test passes, but canonical verification stopped because the task had
reached its maximum three automated repair cycles. OPS-001 is blocked pending
human direction; the latest hardening is not represented as canonically verified.

The repository owner authorized resumption in
<https://github.com/cmbuyamba/keyforta-property/issues/48#issuecomment-5651697302>.
The automated repair count remains capped at three; the authorization permits
verification of the already-strengthened test and does not waive any gate.
Because `blocked` is terminal in the governed lifecycle, OPS-002 is the approved
successor task. This document preserves OPS-001 failures and records OPS-002
verification without rewriting the prior task history.

OPS-002 repair cycle 1 corrected `issueReference` from the authorization comment
URL to the durable base issue URL after agent-governance validation rejected the
comment fragment. The authorization comment remains in approval evidence.

OPS-002 repair cycle 2 addresses the follow-up review mutation where child
completion events could outlive an early parent-shell exit. Failure scenarios now
also require each failed component's post-wait workflow diagnostic, proving parent
control reached the corresponding status check after both guarded waits.

## Security

Permissions, OIDC, environment approval, SHA binding, reviewed-plan binding, and
secret handling are unchanged. Neither deployment image is pushed unless both
concurrent builds succeed.

## Accessibility

No user interface behavior changes.

## Architecture

The workflow topology and deployment ordering remain unchanged. Only independent
container work inside existing steps executes concurrently.

## Infrastructure

No Bicep, Azure resource, database, or environment configuration changes. No

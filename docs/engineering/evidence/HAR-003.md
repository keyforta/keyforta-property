# HAR-003: Scan every retained harness report entry

## Scope

Issue [#6](https://github.com/keyforta/keyforta-property/issues/6) closes the
post-merge retention bypass found after HAR-001. CI uploads the complete
`harness/reports/` directory, so the terminal guard must inspect every retained
entry rather than JSON files only.

## Business invariant

No generated artifact may be retained unless every uploaded entry is a readable
regular file whose path and content pass the repository secret policy.

## Technical decision

- Enumerate every root report entry regardless of extension.
- Scan every regular file path and content with the existing forbidden patterns.
- Treat symlinks, nested directories, special entries, unreadable metadata, and
  unreadable files as unsafe.
- Anchor Linux enumeration to an open source-directory descriptor, open each
  file with no-follow semantics, and verify descriptor identity and stability.
- Copy only the exact scanned bytes into a fresh snapshot tree.
- Build CI snapshots as root under `/var/lib/keyforta-evidence`, with read-only
  files, so same-user processes cannot alter the upload handoff.
- Remove the report set and snapshot on any finding or replacement race.
- Upload only the protected snapshot and preserve all policies and schemas.

## Acceptance-test map

| Acceptance criterion | Requirement | Verification |
| --- | --- | --- |
| `AC-HAR-003-01` | Non-JSON and symlink entries cannot bypass retention scanning. | `harness/scripts/self-test/20-evidence-lifecycle.suite.mjs` |
| `AC-HAR-003-02` | Safe evidence is copied to an isolated upload snapshot while unsafe or raced report sets fail closed. | `pnpm harness:self-test`, `pnpm verify`, `pnpm verify:evidence`, and `pnpm verify:reports` |

## Threat model

An untrusted or defective report producer could write a secret into a non-JSON
file, encode it in a path, or introduce a symlink to content outside the report
directory. Because CI uploads the complete directory, extension-only scanning
would permit that data to be retained. A file could also be replaced between
metadata inspection and path-based reading. The guard now opens with no-follow
semantics and uploads only the exact scanned bytes copied to an isolated tree.

## Security and data impact

The change strengthens artifact confidentiality without changing authentication,
authorization, product data, production data, retention duration, or policy
patterns. Synthetic credentials are used in tests.

## Rollback

Reverting HAR-003 restores the known bypass and should occur only with a
replacement terminal control. No product runtime or deployment rollback applies.

## Implementation evidence

- Added all-extension regular-file scanning and fail-closed entry rejection.
- Added descriptor-anchored Linux traversal and exact-byte snapshot copying.
- Added non-JSON, symlink, unreadable, nested-directory, safe-snapshot, and
  replacement-race regression tests.
- Changed CI to create a root-owned snapshot, upload only that path, and remove
  it after the upload step.

## Failure

Independent security review demonstrated that a regular report could be
replaced with a symlink after metadata inspection and before path-based reading.
It also identified the live source directory as an unsafe upload handoff. A
second review found that path-based parent traversal and a runner-owned staging
tree still permitted pre-upload replacement.

## Bounded correction

The terminal guard anchors Linux traversal to an open directory descriptor,
opens each file with no-follow semantics, verifies its identity and stability,
scans the exact bytes read, and copies only those bytes to a root-owned,
read-only snapshot. CI uploads only that protected snapshot.

## Repair cycle

HAR-003 used two changes-requested cycles: one for the original immutable
scan-to-upload handoff and one for descriptor-anchored traversal plus the
root-owned CI snapshot. The product owner explicitly approved the protected
workflow change.

## Results

Focused harness self-tests, task validation, classification, canonical
verification, evidence validation, terminal retention scanning, GitHub CI, and
independent review are recorded as they complete.

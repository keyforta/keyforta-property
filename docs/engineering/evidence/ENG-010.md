# ENG-010 modular self-test suites

## Scope

Refactor the canonical harness self-test into automatically discovered,
independently owned suites so unrelated harness work does not require edits to
one shared test file.

## Requirements

Keep the existing command, deterministic offline execution, check names and
order, report shape, and fail-closed behavior while removing the central suite
registration bottleneck.

## Risks

Mechanical extraction can silently omit, reorder, or weaken checks. Dynamic
suite loading must remain confined to the repository-owned suite directory and
must reject malformed modules.

## Unknowns

No product, application runtime, persistence, infrastructure, or deployment
behavior is affected.

## Design

Keep `harness/scripts/self-test.mjs` as the stable executable entrypoint. A
dependency-light runner discovers files ending in `.suite.mjs`, sorts them by
filename, validates their exported registration function, and aggregates their
results into the existing report. Shared immutable fixtures and helpers live in
dedicated support modules, while each verification concern owns its suite file.

## Tradeoffs

Automatic discovery removes a shared registry edit and reduces routine merge
conflicts. Numeric filename prefixes preserve the existing output order but
require contributors to choose a stable domain position for new suites.

## Rollback

Revert the extraction commit to restore the monolithic self-test. No runtime,
data, policy, or schema rollback is required.

## Steps

1. Capture the existing ordered check results as the behavior baseline.
2. Add a deterministic suite runner and discovery regression tests.
3. Extract checks into focused suites without rewriting assertions.
4. Document suite ownership and contribution rules.
5. Compare the ordered results and run canonical verification.

## Tests

The focused runner regression creates temporary suites to prove automatic
sorted discovery and rejection of invalid exports. The extracted self-test is
compared with the baseline for check count, names, order, statuses, and report
shape before canonical verification runs.

The clean-checkout regression temporarily removes the ignored
`harness/reports` directory and requires the canonical entrypoint to recreate
it before all 150 suite checks execute.

## Behavior Equivalence

Equivalence requires the pre-refactor and post-refactor reports to contain the
same ordered 150 checks with identical statuses and the same top-level JSON
shape. The canonical command and report location remain unchanged.

## Results

Implementation completed in the allowed paths. The stable executable is 17
lines and delegates to a runner that discovers regular `.suite.mjs` files in
deterministic filename order, rejects any module that does not export only a
`registerSuite` function, and aggregates results through the preserved report
and console contract.

The pre-refactor report was captured at
`/tmp/ENG-010-self-test-baseline.json` with SHA-256
`3e9f8753791bfaeb834a207e01fda4458a92c85b0790c48972f8b3704ec0f290`.
The post-refactor report is exactly equivalent: 150 checks, identical ordered
names and statuses, identical serialized check records, and top-level keys
`checks` and `status`.

Canonical repository verification initially failed before gate execution
because `automatic-suite-discovery` and `behavior-equivalence` were declared as
canonical scenario identifiers instead of acceptance-test behaviors. Both
remain explicitly covered by acceptance criteria and focused tests; the task's
canonical scenario declarations now use only identifiers supported by the
checked-out verifier.

After that bounded correction, required-mode canonical verification passed all
gates against `origin/main`, including repository policy, task contract,
classification, lifecycle, evidence, required scenarios, the 150-check harness
self-test, workspace tests, production builds, and Bicep compilation.

## Failure

The first canonical run rejected two unsupported `requiredScenarios` values and
reported the temporary worktree `node_modules` symlink as outside the task's
allowed paths. No implementation check failed.

Independent review then found that an empty suite directory produced an empty
passing report, which could hide accidental deletion of every self-test suite.

GitHub Actions run `34720410791` exposed a clean-checkout regression: the
extracted entrypoint no longer created `harness/reports` before suite execution,
so four evidence-artifact checks failed with `ENOENT` while writing their
synthetic Markdown fixture.

## Bounded Correction

Keep automatic discovery and behavior equivalence in the acceptance criteria
and focused tests, remove them only from the canonical scenario identifier
list, and replace the temporary dependency symlink with an ignored local
installation before rerunning verification. No verifier, policy, schema, or
application file changes are required.

The review repair makes `runSuites` reject zero discovered suites and adds a
focused regression proving the empty-directory case fails closed.

The CI repair restores report-directory creation before suite registration,
preserving the monolith's original initialization order without changing suite
discovery, checks, policies, schemas, or report semantics.

## Repair Cycle

Repair cycle 1 addressed only the contract declaration and local worktree
dependency setup exposed by the first canonical run. Repair cycle 2 addresses
the independent review's empty-suite fail-open finding. Repair cycle 3 addresses
the clean-checkout report-directory failure from GitHub Actions and reaches the
policy maximum of three automated repair cycles.

## Known Failures

The initial canonical run failed on two unsupported scenario declarations and
the temporary worktree dependency symlink. Both were corrected within repair
cycle 1. Independent review then found the empty-suite fail-open behavior,
which was corrected and regression-tested in repair cycle 2. GitHub Actions run
`34720410791` then failed because a clean checkout lacked the ignored reports
directory; repair cycle 3 restores its pre-suite creation. No known failure
remains after the clean-checkout regression passes.

## Security

No authorization or security policy changes. Suite discovery is local,
extension-constrained, deterministic, and fail-closed.

## Accessibility

No user interface behavior changes.

## Architecture

The canonical entrypoint remains stable while verification ownership moves to
domain-focused foundation, evidence/lifecycle, skill, and agent-governance
modules with no central registration list. Stable synthetic fixtures and result
reporting are isolated from suite ownership.

## Infrastructure

No infrastructure behavior changes.

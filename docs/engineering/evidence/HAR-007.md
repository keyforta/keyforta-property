# HAR-007 trusted report retention controls

## Scope

Issue [#18](https://github.com/keyforta/keyforta-property/issues/18) approves a
security correction for the report-retention findings on PR #13.

## Business invariant

Untrusted pull-request code may produce candidate evidence, but only protected
trusted code may decide which exact bytes are retained.

## Failure

PR #13 freezes its scanner and policy from the pull-request checkout, recursively
changes ownership of an attacker-controlled report root, opens raced entries in
blocking mode, and stops content scanning later files after an earlier finding.
The snapshot path also lacks a secret-bearing non-JSON regression.

## Design

Ordinary CI uploads candidate reports as an explicitly untrusted artifact and
retains read-only permissions with no secrets. A `workflow_run` workflow defined
on the protected default branch downloads that artifact, checks out its own exact
trusted workflow SHA, scans and snapshots every entry, and uploads only the
runner-owned snapshot. The scanner opens entries with no-follow and nonblocking
flags, rejects non-regular descriptors, and tracks findings per entry.

## Acceptance-test map

| Acceptance criterion | Requirement | Verification |
| --- | --- | --- |
| `AC-HAR-007-01` | Retention uses protected trusted code and exact scanned bytes. | Structured workflow regression and GitHub CI |
| `AC-HAR-007-02` | Raced special files cannot block, and all entries are scanned independently. | Evidence-lifecycle self-tests and canonical verification |

## Security

The trusted workflow executes no pull-request code and receives no repository
secrets. Its token is limited to reading source artifacts and uploading the
sanitized snapshot. Missing, malformed, unsafe, or unreadable candidates fail
closed and produce no retained artifact.

## Tests

The focused harness suite covers secret-bearing non-JSON and UTF-16 reports,
FIFO replacement, independent entry scanning, nested failure reports, and the
trusted workflow structure. It passes after the bounded correction.

## Repair cycle

Independent review found that the initial implementation excluded failed CI
runs, rejected canonical nested failure reports, accepted UTF-16/binary bytes,
used mutable action tags, and requested excess artifact permission. Repair cycle
one runs retention after every completed pull-request workflow, traverses nested
directories through opened descriptors, rejects non-UTF-8 or NUL-bearing input,
pins privileged actions to immutable commits, and limits `actions` to read.

## Bounded correction

Architecture re-review found that the correction record would reference a
missing evidence section. Repair cycle two adds this substantive bounded
correction record; it changes no implementation, workflow, policy, schema,
product, data, infrastructure, or deployment behavior.
